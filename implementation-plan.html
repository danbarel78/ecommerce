Infrastructure as Code — Deep Dive

How the Terraform in infra/ is structured, how each module is built, and — the focus here — how arguments and parameters are defined and passed. Everything below is drawn from the real files in this repo; see also IMPLEMENTATION-PLAN.md (the plan) and DEEP-DIVE-REVIEW.md (the review of what's built).

01What the plan is

The plan turns the target-state design in ARCHITECTURE.md into a buildable implementation across four tracks. AWS is the primary cloud; everything is provisioned with Terraform, structured into reusable modules.

A · Infrastructure (IaC) B · Advanced Security C · Cost Optimization D · Product Management API
Guiding principles
  • Everything is Terraform — no click-ops. State in a locked, versioned S3 backend + DynamoDB lock table, one state key per environment.
  • Reusable modules under modules/; thin environment roots under envs/{dev,staging,prod} that only wire modules together with env-specific values.
  • Multi-AZ by default, warm-standby DR (us-east-1 primary, us-west-2 DR).
  • Least privilege everywhere; secrets never in code, state, or images.

02Repo layout

Two top-level trees: infra/ (Terraform) and api/ (the product service).

  backend.tf                # S3 + DynamoDB remote state (partial config)
  versions.tf               # required_version + provider pins
  modules/

    database/               # Aurora PostgreSQL (+ Global DB, RDS Proxy)
    cache-search/           # ElastiCache Redis + OpenSearch
    eventing/               # MSK (Kafka)   [variables only — stub]
    eks/  loadbalancer/  observability/   # [not yet implemented]

ℹ️Each module is a black box with a typed input contract (variables.tf) and a published result set (outputs.tf). Environment roots are where concrete values live; modules carry only safe defaults.

03Anatomy of a module

Every module follows the same five-file convention. This uniformity is what makes the modules composable and reviewable.

FileResponsibility
variables.tfThe module's input contract — every argument it accepts, with type, description, default, and validation.
main.tfThe resources themselves (resource/data blocks), referencing var.*.
outputs.tfValues the module publishes for other modules to consume (ids, ARNs, SG ids).
versions.tfProvider + Terraform version constraints the module needs.
README.mdUsage example + input/output highlights.

A module never hard-codes account-specific values; it declares what it needs and lets the caller supply it. That caller is an environment root (§4.5).

04Defining arguments (variables)

An argument is a variable block. The three parts that matter are type (the contract), description (intent), and default (whether the caller must supply it). Example from modules/network/variables.tf:

variable "vpc_cidr" {
  description = "CIDR block for the VPC. Non-secret; safe default provided."
  type        = string
  default     = "10.0.0.0/16"   # has a default → optional for the caller
}

variable "azs" {
  description = "REQUIRES REAL VALUE — AZ names to span (e.g. [\"us-east-1a\",...])."
  type        = list(string)
  # no default → the caller MUST provide it
}

Inside main.tf the value is read as var.<name>, e.g. cidr_block = var.vpc_cidr. Counts and loops derive from them — the network module builds one subnet per AZ with count = length(var.azs).

4.1 · required vs. default, and the "REQUIRES REAL VALUE" convention

  • No default ⇒ required. Terraform errors at plan time if the caller omits it (e.g. name, azs, master_secret_arn).
  • Has default ⇒ optional. Safe, non-secret defaults are provided so a module is usable out of the box (CIDRs, engine versions, instance classes, retention windows).
  • "REQUIRES REAL VALUE" is a description-prefix convention used across the repo to flag inputs that have no meaningful default and must be supplied per environment (AZ names, KMS key ARNs, secret ARNs, the EKS OIDC provider). It is documentation, not enforcement — grep for it before an apply.
🔎grep -rn "REQUIRES REAL VALUE" infra/ lists every input an environment must fill in.

4.2 · validation & typed object arguments

A validation block rejects bad input early. From modules/security/variables.tf:

variable "waf_scope" {
  type    = string
  default = "REGIONAL"
  validation {
    condition     = contains(["CLOUDFRONT", "REGIONAL"], var.waf_scope)
    error_message = "waf_scope must be CLOUDFRONT or REGIONAL."
  }
}

For richer inputs the type is a typed object (often a map of objects), so the caller passes structured data that Terraform type-checks. The IRSA factory is the clearest example — a map of microservice → role definition:

variable "irsa_service_accounts" {
  type = map(object({
    namespace       = string
    service_account = string
    policy_statements = list(object({
      sid       = string
      actions   = list(string)
      resources = list(string)
    }))
  }))
  default = {}
}

main.tf then iterates the map with for_each to mint one least-privilege IAM role per entry, and a dynamic "statement" block expands each service's policy_statements. Adding a service is a data change in the caller — no new resource code. managed_secrets uses the same pattern with optional(...) fields for rotation.

4.3 · secrets are passed by ARN, never as values

No password or token is ever a Terraform variable value. Instead the security module creates the Secrets Manager container, and consuming modules receive only its ARN:

# database/variables.tf — the ARN is the input, not the secret
variable "master_secret_arn" {
  description = "REQUIRES REAL VALUE — Secrets Manager ARN holding the master password."
  type        = string
}

# database/main.tf — read at apply, and tell TF to stop tracking it
lifecycle { ignore_changes = [master_password] } # rotated via Secrets Manager, not TF
⚠️Reading a secret through a data "aws_secretsmanager_secret_version" source still lands the value in Terraform state. The review (DEEP-DIVE-REVIEW.md, H2) recommends RDS-managed credentials (manage_master_user_password = true) to avoid that entirely.

4.4 · wiring — one module's outputs are another's arguments

Modules connect through outputs.tf. The network module publishes ids other modules require as inputs:

# modules/network/outputs.tf
output "private_data_subnet_ids" {
  value = aws_subnet.private_data[*].id
}
# modules/database/variables.tf consumes it as `subnet_ids`

The env root threads them together (see §4.5): subnet_ids = module.network.private_data_subnet_ids. Terraform reads this dependency graph to order the applies automatically.

4.5 · environment roots & tfvars

An env root is a thin file that instantiates modules and supplies the per-env values. The envs/* dirs are currently empty — this is the intended pattern to add (labelled illustrative):

# envs/dev/main.tf  (intended — not yet present)
module "network" {
  source             = "../../modules/network"
  name               = "ecommerce-dev"
  azs                = ["us-east-1a", "us-east-1b", "us-east-1c"]
  single_nat_gateway = true          # dev cost lever (Track C)
  tags               = { env = "dev", service = "platform", owner = "team-x" }
}

module "database" {
  source            = "../../modules/database"
  name              = "ecommerce-dev"
  vpc_id            = module.network.vpc_id              # ← wiring
  subnet_ids        = module.network.private_data_subnet_ids
  master_secret_arn = module.security.db_master_secret_arn
  kms_key_arn       = module.security.kms_key_arns["database"]
  enable_global_db  = false         # dev: no cross-region DR (cost)
}

Static, non-secret values that vary by env live in terraform.tfvars; a value can also be overridden at the CLI (-var) or via TF_VAR_*. Precedence, low→high: variable default → terraform.tfvars → -var-file → -var/TF_VAR_*.

05State backend & version pinning

State is remote and locked. The backend uses a partial configuration — no account-specific values are committed; they're supplied at init time:

# backend.tf
terraform {
  backend "s3" {
    encrypt = true
    # bucket / dynamodb_table / region / key via -backend-config
  }
}
# init:
terraform init \
  -backend-config="bucket=…-tfstate" \
  -backend-config="dynamodb_table=…-tf-lock" \
  -backend-config="key=ecommerce/dev/terraform.tfstate"

Provider and core versions are pinned in versions.tf (aws ~> 5.40, terraform >= 1.5.0) so plans are reproducible.

08Module: database

Aurora PostgreSQL, multi-AZ, optional Global DB + RDS Proxy. substantive

BuildsKey params
Aurora cluster + replica_count+1 instances across AZs · optional Global DB (DR) · optional RDS Proxy (TLS + IAM auth) · encrypted at rest (CMK) · PITR subnet_ids/vpc_id (from network) · master_secret_arn, kms_key_arn (from security, req) · instance_class · replica_count · enable_global_db · enable_rds_proxy · deletion_protection · backup_retention_days

09Module: cache-search

ElastiCache Redis + OpenSearch, both multi-AZ and encrypted. substantive

BuildsKey params
Redis replication group (cluster mode; auth token from secret; at-rest+transit encryption; multi-AZ failover when replicas ≥ 1) · OpenSearch domain (zone-aware, node-to-node + at-rest encryption, enforce HTTPS) redis_node_type · redis_num_node_groups · redis_replicas_per_node_group · redis_auth_secret_arn · opensearch_instance_type/_count/_az_count · kms_cache_key_arn · kms_search_key_arn

Redis holds sessions, cart, hot-product cache, and the stock-reservation counters (the corrected §4.1.4 inventory model). redis_replicas_per_node_group >= 1 is what flips on multi-AZ automatic failover.

11Tracks B / C / D — where they live in params

Track B — Security

Expressed through the security module: IRSA least-privilege roles, per-domain KMS CMKs, Secrets-by-ARN, and WAF. Least privilege is enforced by the shape of irsa_service_accounts (explicit actions/resources, no wildcards).

Track C — Cost

Expressed as parameters, not separate code: single_nat_gateway, instance_class, redis_node_type, opensearch_instance_type, enable_global_db, replica_count. Dev sets the cheap end; prod overrides.

Track D — Product API

A FastAPI CRUD service (JWT via Cognito JWKS, slowapi rate limit, SQLAlchemy → Aurora, pytest ≥80%). not built — api/product-service/ is empty.

Track A — IaC

The modules above + the env roots that compose them. Four modules done; eks/loadbalancer/observability and all env roots remain.

13How to run (once an env root exists)

# from the env root, e.g. infra/envs/dev
terraform init -backend-config="…"   # wire remote state
terraform fmt -recursive && terraform validate
terraform plan  -out tfplan            # preview; fill every REQUIRES REAL VALUE first
terraform apply tfplan

Execution order (from the plan): foundation (state, network, security) → data + compute (database, eks, cache-search, eventing) → edge (loadbalancer + WAF + Cognito) → API → cost/ops → DR & hardening.
