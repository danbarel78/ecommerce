§1.2 · Problem Statement

Why the naïve approach fails

📈Highly variable traffic — flash sales & Black Friday drive 10–50× baseline in minutes. Static provisioning wastes money or falls over.
💸Downtime = lost revenue. A checkout outage at peak is business-critical — single AZ / region / DB are unacceptable SPOFs.
🕸️Monolithic coupling — a failure in reviews/recommendations can take down the checkout critical path.
🔒Vendor lock-in to proprietary services raises long-term cost, migration risk, and weakens negotiating position.
🛡️Security & compliance — PII and payment flows demand defense-in-depth, encryption everywhere, least-privilege by default.

§3 · Assumptions & Prerequisites

What we assume going in

§4.1.4 · Domain Class Diagram

Entities & architectural invariants

// core domain entities Customer { id, email, status } └─ 1..* Cart { id, customerId, subtotal() } └─ 1..* CartItem { sku, qty, unitPrice } └─ *..1 Product { sku, title, price } └─ 1..1 Inventory { available, reserved } └─ 1..* Order { id, status, total, placedAt } ├─ 1..1 Payment { orderId, status, providerRef } └─ 1..* CartItem (snapshot)
Service interaction rules
①Only the Order service writes order and payment rows (one txn). Payment is stateless — no dual-write.
②Cart lives in Redis (async persistence) — ephemeral, cache-like, not source of truth.
③Stock reserved synchronously in Redis (DECR stock:{sku}, reject if negative) — prevents oversell on the hot path; Aurora reconciled asynchronously by the stream consumer.
④Every state change publishes an event to Kafka; consumers are the only writers to their own projections.
⑤No service calls another service's database. "Database-per-service" is logical — own schemas within one Aurora cluster; cross-service data via REST or Kafka.

§4.2 · Order State Machine

Order lifecycle

The lifecycle is explicit because it drives correctness — including the compensation path.

created→ stock_reserved→ payment_pending→ paid→ placed→ fulfilled
rejected
from created when DECR would go negative — out of stock, before any charge.
payment_failed
from payment_pending when the provider declines. No order persisted.
compensating → voided
from paid when the order write fails — auto-void/refund + release reservation (§4.3.1b).
🧭cancelled is reachable from placed (customer or fraud). Every transition emits an event, so downstream projections stay consistent with the order's true state.
